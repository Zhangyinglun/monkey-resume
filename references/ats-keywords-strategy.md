# Matching JD requirements to evidence

Analyze the original JD's responsibilities, required capabilities and preferences.
Prioritize actual importance, not keyword frequency. Save those requirements in
the draft's `target`; the original text remains the authority.

Inspect complete active evidence, not only search results for the JD's words:

- **Direct**: actual work satisfies the requirement.
- **Equivalent**: the same professional capability has different wording; use
  standard language only when supported by the original meaning.
- **Transferable**: related work shows relevant capability but not necessarily
  the named tool or full responsibility. Make its actual scope clear.
- **Gap**: no adequate evidence exists. Do not create a skill to fill it.

These categories support model reasoning; the writer need not create a separate
capability JSON or fill every row with a keyword. Requirements in a draft can use
P1/P2/P3 to convey core/important/supporting priorities.

Kafka event integration does not establish broker administration. Kubernetes
deployment does not establish Helm/Operators or infrastructure as code. Multiple
tools and metrics occurring in the same employer do not establish that they were
used together on the same project.

Reuse confirmed answers and explicit denials. Clarify only important missing facts
whose answer changes selection or accuracy, and keep the original excerpt when
ingesting answers. Protected attributes do not determine matching. Literal keyword
coverage is a diagnostic, never an ATS score or probability of being hired.
